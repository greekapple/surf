# Cold Home slow tail on production (diagnosis, 2026-11-14)

Read-only diagnosis. No code was changed. Production is `https://swello.surf-prototype.workers.dev` (behind Cloudflare Access, service token from the keychain, never printed). Numbers below are from this morning, 04:50 to 05:10 PST (12:30 to 13:10 UTC).

## Answer in one paragraph

The stall is **one Worker request: the 12-key batch `GET /api/providers?keys=ndbc-46042,ndbc-46236,nearshore-SF023-forecast, ... nearshore-MA142-forecast`** (2 NDBC buoys and 10 CDIP MOP nearshore forecasts). In the slow run it got **no response for 20.006 s** and the app's own 20 s batch timeout (`BATCH_TIMEOUT_MS`, `src/ocean/providerBatch.ts:5`) aborted it, then asked each key on its own and those answered in 55 to 190 ms. The Home best bet appeared 0.6 s after that. It is **not** Open-Meteo (all the marine, weather and spread batches finished in 0.06 to 0.9 s), not tides, not the frames, not the SRF call. Within the batch, **three keys hang inside the Worker: `nearshore-SF015-forecast`, `nearshore-SF053-forecast`, `nearshore-SM402-forecast`**. The upstream they depend on (CDIP THREDDS) answers my machine in 0.15 to 0.24 s for those same three ids, so the hang is in the Worker or between the Worker and CDIP, not in CDIP being slow for everyone.

## Method

1. `coldhome.mjs` (lead's) copied and instrumented, 10 cold loads of Home at 390 x 844, fresh context each, every request timed (start, end, status, time to first byte, cache header). Script: `/private/tmp/claude-501/wq/coldtail/coldtail.mjs`, raw data `/private/tmp/claude-501/wq/coldtail/runs.json`.
2. Direct probes with curl against the Worker, then against CDIP, using the same URLs the Worker uses.
3. Read the Worker code: `services/forecast-service.mjs` (`retrieve`, the `/api/providers` handler) and `src/ocean/providerBatch.ts`.

### The Worker keeps hanging on the same three keys

Straight after, from curl (not the browser), the same 12-key batch URL, 20 tries 2 s apart, 25 s cap: **10 of the first 12 tries got no response in 25 s**; the two that answered did so in 0.22 and 0.73 s (865 KB). I stopped the loop after 12 to avoid loading the Worker.

Each of the 12 keys on its own (`/api/provider?key=K`, 30 s cap):

| key | result |
|---|---|
| ndbc-46042, ndbc-46236 | 200 in 0.18 s, `cache: fresh`, retrieved 12:21 and refreshed 12:36 UTC |
| nearshore SF023, SF041, MA048, SM387, SM382, MA121, MA142 | 200 in 0.11 to 0.28 s, `cache: fresh`, retrieved 11:52 to 12:16 UTC (inside the 1 h TTL) |
| **nearshore SF015, SF053, SM402** | **no response in 30 s** |

So the keys that are inside their cache window answer instantly and the three that hang are the ones with no answerable cache entry. CDIP itself is fine from here: `thredds.cdip.ucsd.edu/.../MOP_alongshore/{SF015,SF053,SM402}_forecast.nc` (the exact request the Worker builds) returned 200 in 0.19 to 0.24 s.

One more observation: `GET /api/diagnostics` (reads every key) did not answer within 40 s, which fits a Worker that is waiting on something, but it is a heavy endpoint, so this is weak evidence.

## What the code says (why one key can stall a whole batch)

1. `/api/providers` (`services/forecast-service.mjs:222`) retrieves its keys 3 at a time and **awaits all of them with no per-key deadline**; one stuck key holds the whole response, including the 11 healthy ones.
2. `retrieve()` (line 120) keeps an `inflight` map per isolate: a second request for the same key **awaits the first one's promise**. If that promise never settles, every later request for that key in that isolate hangs with it, until the isolate is recycled. That matches "the same three keys, over and over, for many minutes, while two curl tries got through" if requests land on different isolates.
3. An upstream fetch is bounded by `AbortSignal.timeout(18000)` and retried once for upstream or network errors (lines 132 to 138), so even a well-behaved failing key can take about 18 s + 0.25 to 0.75 s + 18 s, which is more than the app's 20 s, so the app gives up first.
4. The app's batch timeout is 20 s and the fallback per key is fast, so a stalled batch costs exactly 20 s plus a second.

## What is established and what is not

Established (measured): the stalled request, its duration, that the app falls back and recovers at 20 s, that the three keys hang from outside, that CDIP answers directly in about 0.2 s, and that nothing else on the page is slow.

**Not established:** why those three keys never settle inside the Worker. Candidates, in the order I would check them:

1. **The refresh of a stale key hangs and never reaches the 18 s abort or the failure record.** The keys that answer are exactly the ones inside the 1 h TTL, so they never touch CDIP; the three that hang are probably stale and trigger an upstream fetch. A hang after headers (the body read, `await response.text()`) is not clearly covered by the abort signal in the Worker runtime. I did not verify that.
2. **CDIP throttles or stalls Cloudflare egress for some requests** while serving my IP normally. A direct request from my machine cannot rule this out.
3. **An R2 `get` or `put` hangs** for those keys (the failure record or snapshot object). Nothing here distinguishes it from 1.

A Worker log for one affected key would settle it; I did not have one. `wrangler tail` while hitting `/api/provider?key=nearshore-SF015-forecast` would show whether the fetch starts, returns headers, or never returns. I did not run it.

## For Track 0 (suggestions, nothing implemented)

1. **Give every key a deadline inside the batch** (for example 6 s) and return `{status: 504}` or the stale snapshot for that key, so one bad key cannot hold 11 good ones.
2. **Make the single-flight promise time out** so a hung job is dropped and the next request starts a fresh one.
3. **Lower the app's batch timeout** from 20 s to about 5 or 6 s; the per-key fallback already recovers in under 200 ms, so a 20 s wait buys nothing.
4. **Do not gate Home's best bet on nearshore and buoy keys.** All the Open-Meteo data it needs was in by about 3.4 s in the slow run.
5. **Keep the 10 nearshore keys warm on the cron** so a user request never has to refresh one, and look at why the cron left SF015, SF053 and SM402 stale (check their failure records in R2).

About 10 cold page loads, 12 batch requests (10 of which hung to the 25 s cap), 12 single-key requests and one diagnostics request, all read-only GETs of public ocean data through the Worker. I did not retry in a loop after the pattern was clear.
