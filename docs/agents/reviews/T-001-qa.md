## Visual findings (viewed m390-week, m390-context, d1440-week)
- Layout is clean at 390: spot name as heading, 2-column grid of day cells, day label above each cell, 16px gutters, no clipping.
- Rating dot: NOT visible on mobile, and NOT visible on desktop either. `.cell b i` computes to width 0 / height 16 / display inline on every viewport, so the coloured dot before "Not bad" / "Solid" never renders. Colour is carried only by the 3px top bar and the tint. This is a parity issue, not a regression from T-001, but a demanding user expecting the dot (as the brief assumed) will not see it. Defect D1 (low).
- Section length: week block is 1025px tall at 390 (page 4460px), about 1.2 screens. Reasonable, though 3 spots x 3 rows of 2 days is long; the same cell type repeated 18 times is monotonous. Optional improvement (nice-to-have): 3-column grid would cut about 1/3 of the height at 390 (cells would be about 112px wide at 360, which is tight).
- At 820 (tablet, under 860) the cells are 373px wide in the 2-column stack and the layout looks sparse. A 3-column grid between 600 and 860px would be better (nice-to-have, D2).
- Sticky bottom tab bar overlaps content in viewport captures only; normal.

## Defects
- D1 (low, pre-existing, both layouts): the rating dot `<i>` has zero width. Repro: open Home at any viewport, inspect `.week button.cell b i`: getBoundingClientRect width 0. Expected: a small coloured dot before the rating word. Actual: nothing. Evidence: m390-week.png, d1440-week.png. Likely missing `display:inline-block; width:..; height:..` or the rule is absent in home.css (production fix needed; not mine to apply).
- D2 (nice-to-have): 820px tablet shows a 2-column stack of very wide cells (t820-week.png), 1025px tall.
- No blocking defects for T-001.
