# Map findings (map-seamless, stage 0)

Written 2026-11-04 on branch `map-seamless` (forecast-trust 46ebec1 + this note). Brief: `docs/specs/2026-11-04-map-seamless.md`. Everything marked **measured** was measured this session with the probe scripts named at the end (live NOAA/PacIOOS data, our dev server, headless Chrome); everything marked **code** is read from the source with the file named. Nothing here was changed in the app yet.

## 1. How the map works today

- **Library:** Leaflet 1.9 (`src/features/explore/ExploreView.tsx`, `L.map` with `minZoom 2`, `maxZoom 14`, `zoomSnap 0.5`, `worldCopyJump`, `maxBounds [-85,85] × [-540,540]`, `maxBoundsViscosity 0.8`). One map instance per `OceanMap` mount.
- **Basemap:** Esri Canvas **raster** tiles (`src/map/basemap.ts`): a base layer (light/dark grey, or the dark grey canvas filtered to mid-grey while the field is on) and a separate Reference **labels** layer in its own pane above the field. `maxNativeZoom 13` (tiles are scaled past that). Both layers are `PaddedTileLayer` (T-115: loads a ring of tiles 40% of the viewport wide) with `updateWhenZooming:false`, `keepBuffer 8`.
- **Data:** WW3 from the PacIOOS/University of Hawaii server on NOAA's ERDDAP (`NWW3_Global_Best`; wind from `NCEP_Global_Best`, i.e. GFS). Two frames per view, fetched as JSON tables (`src/map/spatial.ts`): a **regional** frame (32–42.5°N, 127–117°W at the native 0.5°, 462 cells, ~25 KB) and a **global** frame through `/api/globe` (`services/forecast-service.mjs`): the native 0.5° grid read with a stride of 4 (**2°**, lat −76..76, 180×77 = 13,860 cells, ~700 KB JSON), cached in memory per (field, time). Valid times are 3-hourly (floored to 10,800,000 ms).
- **Decode and grid:** on the main thread (`normalizeGrid`, `buildField` in `src/map/fieldData.ts`): JSON rows → a regular lat/lon `Float32Array`, then **NaN cells are filled from their neighbours in up to 8 passes** (8-neighbour average).
- **Draw:** Canvas 2D, not WebGL (`src/map/field.ts`). The heat canvas is drawn at the viewport plus a 50% pad: for every 4 px (6 px on a big canvas) cell the field is sampled (bilinear, regional first, then global), coloured through a 256-step lookup table, put into a small `ImageData`, scaled up with `ctx.filter = blur(1.25 × step px)`, and then the land is cut out with `destination-out` using coastline polygons (`coast.json`, 1,883 points for California; `land-globe.json`, 553 rings / 35k points for the world). The enclosed-water mask (T-092) hatches bays. It redraws on `moveend`/`zoomend` (one coalesced `requestAnimationFrame`); during a zoom the canvas rides Leaflet's zoom animation (T-115). Redraw cost: measured 15–20 ms desktop, 35–40 ms iPhone profile at 4× CPU.
- **Colour and legend:** `src/map/colors.ts` (Windy's ramps, T-115/T-117) and `RANGE` / `RANGE_WIDE` in the same file; the legend (`LegendChip`) reads `rampFor(unit, wide)` and `legendEnds`.
- **Particles:** a second 2D canvas (`xfield-flow`): waves/swell/period are 6 px white dashes (≤ 1,400, drift 0.35 px/frame, life 150 frames), wind is streamlines with fading trails (≤ 2,200).
- **Routing and layers:** `ExploreView` renders `OceanMap` for `/explore`, `/explore/wind`, `/explore/swell`; the layer is `fieldId` state derived from the section (`ExploreView.tsx:68`), so the same component stays mounted. State in the URL: path (layer) and `?spot=` only.
- **Spots:** Leaflet DOM markers (`L.marker` with a DivIcon: dot + label). `declutter()` (`ExploreView.tsx:208`) measures the DOM boxes, orders by selected > rank, hides labels that collide with each other, with the sheet, search, buttons, attribution and the spot popup, and caps labels by zoom (`labelBudget`).
- **Point values:** `sampleField` (T-117, `src/map/field.ts`) samples the same grids the painter uses; the point label/panel is the product side.

## 4. Proposal (a): Leaflet → MapLibre GL

**What forces the question.** Two items in the brief are hard on a raster Leaflet map: crisp labels (measured above: raster label tiles from two zoom levels coexist ~1 s while zooming) and GPU particles with trails over a GPU-drawn field (Leaflet has no WebGL layer API or camera matrix; a WebGL canvas can be hosted as an overlay, but it must be re-synchronised by hand with Leaflet's CSS-transformed panes on every frame, which is what causes the usual "swimming" of overlays during zoom).

**Options.**

| | A. Stay on Leaflet, fix the raster transitions | B. Hybrid: Leaflet UI + `@maplibre/maplibre-gl-leaflet` vector basemap | C. Full MapLibre GL JS |
|---|---|---|---|
| Crisp labels | partly: never composite two label levels, fade children in; still raster, still blurry between levels | yes (vector symbols) but the GL canvas is a layer inside Leaflet's panes, with the same zoom-sync caveats | yes, native |
| GPU field + particles | extra WebGL canvas hand-synced to Leaflet | same | `CustomLayerInterface` shares the map's camera matrix: no sync code |
| Globe (Stage 7) | no | no | yes (globe projection in v5) |
| Marker/label collision | our DOM `declutter()` | same | built-in symbol collision and priority |
| Bundle (gzip, measured from published builds, to re-measure in a spike) | Leaflet ~42 KB | ~42 KB + ~220 KB GL | ~220 KB GL instead of Leaflet |
| Work | days | ~1 week | ~1.5 to 2 weeks: `ExploreView.tsx` (491 lines) uses Leaflet's markers, popups, panes, `flyTo`, `fitBounds`; `field.ts`'s projection calls become shader maths; the pure modules (fields, ramps, `sampleField`, tests) carry over unchanged |
| Risk | low, but the brief's targets are not reachable | medium: two engines | medium: one engine, one rewrite of the view layer |

**Basemap licensing (vector).** OpenFreeMap (free, no key, OpenMapTiles schema; data ODbL, attribution required), Protomaps PMTiles self-hosted on our storage (ODbL data, a few GB, no per-request cost), MapTiler (key, free tier, paid for commercial volume), Esri vector tiles (ArcGIS account/key). None is licensed or paid for yet; nothing is added without the user's OK. Esri raster tiles stay until then. Our two grey variants (light, dark) become a style JSON we own.

**Recommendation.** Option C, in its own branch after Stages 1 and 3, because Stage 2's GPU field and Stage 4's particles want the camera matrix and the label problem is only fully solved by vector symbols; B is the fallback if the user prefers a smaller change, A will not reach the brief. A one-day spike (a MapLibre map with our current grey style, the field as a custom layer and the existing `sampleField`) would give the real bundle size, frame rates on the phone profile and the effort estimate before committing. **Decision needed from the user: C, B or A; and whether a spike is OK.**

## 5. Proposal (b): a higher-resolution global wave source and a tiled pre-processing pipeline

**What we use now.** PacIOOS/UH WW3 on ERDDAP: 0.5° global (720×311, lat ±77.5), `time_coverage_end` 2026-11-10 (about a week), forced by NOAA/NCEP winds, free to use and redistribute ("not intended for legal use"); the client pulls a JSON table per view (700 KB for 2°, the full 0.5° as JSON would be ~11 MB, too big, hence the stride).

**Options (all verified listed on 2026-11-04 unless noted).**

| Source | Resolution | Cadence / range | Latency | Licence | Cost |
|---|---|---|---|---|---|
| **NOAA GFS-Wave (WW3)**, NOAA Open Data on AWS `noaa-gfs-bdp-pds`: `gfs.YYYYMMDD/HH/wave/gridded/gfswave.tHHz.global.0p16` and `.0p25` (GRIB2; also `arctic.9km`, `atlocn.0p16`, etc.) | **0.16° (~18 km) and 0.25°** global | 4 cycles/day; hourly then 3-hourly (the 00z listing shows f000 to at least f132, hourly steps then steps of 2 and 3); each file about 10.7 MB (0p16) or 11.3 MB (0p25) with all variables, `.idx` files allow byte-range downloads of just Hs, Tp, Dp, swell partitions and winds (~1 MB each) | about 4 to 5 h after the cycle (NCEP) | US government work, public domain; AWS Open Data programme: no restrictions | free to read; our compute and storage only |
| **ECMWF open data** (`ecmwf-forecasts` bucket, `YYYYMMDD/00z/ifs/0p25/wave/…grib2`, about 5.4 MB per step) | 0.25° | 00/12z to 360 h (06/18z shorter), 3 to 6-hourly | about 7 to 9 h (today's 00z was not yet listed when checked) | CC BY 4.0 per ECMWF's open-data page (to be re-read before use) | free |
| **Copernicus Marine** `GLOBAL_ANALYSISFORECAST_WAV_001_027` (MFWAM) | 1/12° (~9 km) | 3-hourly, ~10 days | hours | free with registration, attribution, commercial use allowed | free; needs an account and credentials (kept as a CI secret, never in the repo) |
| Open-Meteo Marine API | per point | hourly | minutes | free tier is non-commercial / rate limited; paid above | not a grid service, no |

**Recommended source:** GFS-Wave **0.25°** as the primary global grid (public domain, same family as the WW3 we already use, byte-range access to just the fields we draw, 0.16° available later), keeping the current ERDDAP/MOP feeds for the California nest and the spot work. Resolution gain: 0.25° is 8× the 2° stride we show and 2× the native 0.5° the current service could give us without any new source.

**Pipeline (not built).** A scheduled job (GitHub Actions cron or a Worker cron) per cycle: (1) read the `.idx`, byte-range the wanted GRIB2 messages (Hs, Tp, Dp, wind-sea/swell Hs-Tp-Dp, 10 m u/v) for the next ~7 days at 3-hourly steps; (2) decode with `wgrib2` or `eccodes`; (3) repack each (field group, hour) into **one 16-bit/RGB-packed PNG** at 0.25° (1440×721 ≈ 1.0 M cells; roughly 1.5 to 3 MB per PNG after compression), with a small JSON manifest (run time, valid times, value scale and offset); (4) upload to object storage behind a CDN; (5) keep two runs, delete older ones. At 0.25° a **single global texture per frame** is enough, so no tile pyramid is needed (a pyramid only becomes necessary at 0.083° or finer). The client then fetches one or two PNGs per frame (cacheable, immutable per run) and uploads them as textures: no JSON, no ERDDAP per view, decode in a worker, and the CDN absorbs the traffic (our quota problem with Open-Meteo/ERDDAP goes away for the map).

**Estimates (to be confirmed by a one-run dry run).** Storage per run: ~56 frames × 3 packed fields × ~2 MB ≈ 300 to 350 MB; two runs kept ≈ 0.7 GB. On Cloudflare R2 (≈ $0.015 per GB-month, no egress fee) that is cents per month; on S3 plus CloudFront a few dollars per month at low traffic. Compute: GitHub Actions free tier covers 4 runs a day (a few minutes each). Latency to the user ≈ 5 to 6 h after the model cycle (NCEP 4 to 5 h plus processing) versus ERDDAP's own delay today.

**Open points before building.** Where to store (we have no object storage yet), whether a scheduled job may run in GitHub Actions for this public repo, GRIB2 decoding in CI, and attribution wording. **Decision needed from the user: go/no-go on GFS-Wave 0.25° + the job, and on creating storage (a small recurring cost).** Until then Stage 2 stays on the current data.

## 6. What can ship without either decision
